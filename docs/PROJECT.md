# 项目文档 · shake-cursor

> 摇一摇找鼠标：把 macOS 的「晃鼠标 → 指针变大」搬到 Windows。
> 本文记录这个项目的**设计取舍、版本演进、踩过的坑和工程约定**，目标是让后来者（包括未来的自己）
> 不用重读 1800 行代码就能理解"为什么是这样写的"。
>
> 用户手册见 [README.zh-CN.md](../README.zh-CN.md)，变更明细见 [CHANGELOG.md](../CHANGELOG.md)。

---

## 1. 项目定位

| 项 | 内容 |
| --- | --- |
| 解决的问题 | 4K / 多显示器下鼠标指针太小，一转眼就找不到 |
| 解法 | 快速左右晃动鼠标 → 指针瞬间变成实心大箭头 → 停留约 0.7 秒后自动缩回 |
| 平台 | Windows 10 / 11 |
| 技术栈 | Python 3 + `ctypes` 直调 Win32，**零第三方依赖** |
| 形态 | 单个 `shake_cursor.pyw`（1820 行）+ 若干 `.bat` 启动器 |
| 分发 | 绿色免安装，双击即用；可选当前用户级开机自启 |
| 协议 | MIT |

**"零依赖"是硬约束**，不是顺带的结果。它决定了后面几乎所有技术选择：
不引入 PyQt（界面靠原生菜单）、不引入 numpy（图像用 GDI + 手写合成）、不引入 pystray（托盘直接调 `Shell_NotifyIcon`）。

| 版本 | 主题 | 一句话 |
| --- | --- | --- |
| 1.0.0 | 核心效果 | 摇动识别 + 放大渲染 + 指针还原 + 看门狗 |
| 1.1.0 | 场景感知 | 打游戏 / 全屏看片 / 投屏时不响应 |

### 1.0.0 — 核心效果

- **摇动识别**：逐轴统计折返次数，而不是判断速度。
- **放大渲染**：GDI 几何在 4 倍超采样下绘制后降采样，预渲染 21 个尺寸。
- **指针还原**：`SetSystemCursor` 换成全透明指针实现"隐藏"，动画结束再换回。
- **看门狗**：子进程守着管道，主进程无论如何退出都能把指针还原。

### 1.1.0 — 场景感知

反馈原话是「打游戏这些场景下不需要鼠标变大」。这确实是硬伤：大箭头正好盖住准心。

三层判断（细节见 §4.4）：
1. `SHQueryUserNotificationState` —— Windows 自己压制通知用的 API；
2. 前台窗口是否铺满显示器（兜底）；
3. 进程黑白名单（用户可控）。

配套 `--why` 诊断命令 —— 这是这一版最有价值的部分：用户能自己查"我那个游戏为什么没被识别"。

### 1.2.0 — 托盘菜单

1.1.0 把能力做出来了，但入口是 `settings.json`——**没人会去改**。于是加托盘图标：
状态行、暂停、开机自启、**当前程序不弹**（一键拉黑前台进程）、打开配置/日志、退出。

### 1.3.0 — 外观自定义

指针从"永远黑色、永远 3 倍"变成可调：1.5×–5×，以及黑/白/荧光绿/亮橙/天蓝/品红 + 系统取色器。

这一版真正动的是渲染层的合成方式 —— 见 §4.2。

### 1.3.1 — 交互修复

用户报：菜单没点就自己弹出来、而且关不掉。根因是两个 Windows 行为被忽略（§6.4、§6.5）。

同时加了**自动重启**：运行中的实例发现源文件被替换，会自己交接给新进程，用户不用手动重开。

## 4. 核心机制

### 4.1 摇动识别：为什么用折返计数，而不是速度

最直觉的做法是"速度超过阈值就触发"，但实测会大量误触：快速拖窗口、画圈、手抖都可能瞬时高速。

现在的实现（`AxisShake`）逐轴统计：

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `SHAKE_MIN_RUN` | 14 px | 单程位移小于这个不算一次有效折返 |
| `SHAKE_WINDOW` | 0.6 s | 统计窗口 |
| `SHAKE_REVERSALS` | 3 | 窗口内需要 3 次折返（≈ 来回晃 1.5 下） |

X、Y 轴各自独立判定，任一命中即触发 —— 所以横着晃、竖着晃都行，斜着晃更容易命中。

**代价**：判定阈值是常量，没法适应所有人。灵敏度目前只能改代码（后续方向见 §13）。

#### 一次失败的重构（1.4.0 → 1.5.1 回退）

值得留档，因为它解释了两个参数为什么是现在这个值。

| 版本 | 改了什么 | 结果 |
| --- | --- | --- |
| 1.4.0 | 反向 12px 就算折返；窗口改「动作时间」；允许抬手指停顿；加灵敏度三档 | 触控板能触发了，但**日常操作频繁误触** |
| 1.5.0 | 判据换成「振幅 ≥45px 且 路径/振幅 ≥2.5」，折返降级为前置条件 | 误触挡住了，但手感仍不符合预期 |
| 1.5.1 | **整段回退到 1.3.2** 的实现与参数 | 换回稳定性，接受触控板不灵、画圈可能误触 |

1.4.0 的根因值得记住：**把折返的判定阈值降到 12px，等于让「折返」失去含义** ——
移动光标时冲过头再回调 45px、原地抖 12px，都能凑出「3 次折返」。
教训是：判定阈值和判据本身要分开设计，放宽阈值救不了弱的判据。

被回退的实现保留在 `0c74018` / `631f7bc` 两个提交里；`tools/test_shake.py`
（合成轨迹测试，能复现上述两种误触）也在 `631f7bc` 中，将来重启这项工作时应先把它取回来。

#### 与 PowerToys 的算法对比

PowerToys 的「鼠标查找」也支持摇动激活，源码在 `src/modules/MouseUtils/FindMyMouse/`
（源自 Raymond Chen 的 SuperSonar）。它的判定是：

```
在 m_shakeIntervalMs（默认 1000ms）窗口内：
  distanceTravelled / hypot(包围盒宽, 包围盒高) > m_shakeFactor/100
  且 distanceTravelled >= m_shakeMinimumDistance
```

也就是**路径长度 ÷ 包围盒对角线**，配合一个**总路程下限**。
(1.5.0 的「路径/振幅」判据本质上和它同源 —— 只是当时不知道。)

用同一批 12 条合成轨迹横评（`%TEMP%\compare_algos.py` 可复现）：

| 判据 | 符合预期 | 短板 |
| --- | --- | --- |
| **v1.3.2（现行）** | **9/12** | 触控板多段滑动不触发；画圈误触 |
| PowerToys（下限 1000px，系数 2.0） | 8/12 | 幅度 70px 的鼠标晃动**不触发**；画圈误触；长停顿后仍触发 |
| PowerToys（下限 400px） | 9/12 | 画圈误触；长停顿后仍触发 |
| 1.5.0 形状判定 + 主导轴 | **12/12** | 仅合成轨迹验证，未经长期实机检验 |

结论：**PowerToys 的判据并不比我们的更强** —— 它同样会误触发画圈，而且对幅度较小的鼠标晃动不敏感，
因为它靠"总路程下限"当保险，而总路程和"是否在晃"并不是一回事。
它的思路里唯一值得吸收的是**总路程下限**（我们用的是"单轴振幅下限"，两者互补），
但在现有轨迹上没有可观测收益，暂不引入。

### 4.2 放大渲染：双层覆盖 + 逐通道合成

一个带抗锯齿的"实心箭头 + 白描边"看起来简单，但直接 `Polygon` 画两遍边缘会脏。做法是：

1. 在 **4 倍超采样** 的画布上分别画两个尺寸的同一多边形：
   - 图层 A：多边形 + 加粗描边（对应"白色描边"区域）
   - 图层 B：多边形本身（对应"实心"区域）
2. 两张图各自 `StretchBlt` 降采样，得到两张 **覆盖度图**（covA、covB）。
3. 逐像素合成，按通道预乘：

```
outline_pm = covA * (255 - covB) / 255
alpha      = covB + outline_pm
premul.R   = fill.R * covB / 255 + outline_pm
（G、B 同理）
```

**1.3.0 之前的写法**是把同一个灰度值同时写进 R/G/B（因为实心永远是黑的，等价）。加颜色支持时这里必须改成逐通道，否则选红色会得到灰色。

**白描边始终保留**，不跟随填充色。试过"描边自动反色"，但在渐变壁纸上反而更糊 —— 固定白色是更稳的取舍。

### 4.3 隐藏真指针与看门狗

放大时如果真指针还在，小箭头会叠在大箭头里。做法是用 `SetSystemCursor` 把系统箭头换成**全透明光标**。

风险很明确：**主进程崩在这一步，用户就再也看不见鼠标了**。所以配一个看门狗子进程：

- 主进程启动时 `Popen` 一个自己（`--watchdog`），并保留 stdin 管道；
- 子进程阻塞在管道上读；
- 主进程**无论怎么死**（崩溃、被杀、断电除外），管道都会关闭，子进程立即调 `restore_system_cursor()`。

这也是为什么 `_WATCHDOG` 必须存全局引用 —— 否则 `Popen` 对象被回收会顺带关闭管道，看门狗会误判主进程已死而提前还原。

### 4.4 场景感知：三层判定

只在**摇动已被识别、即将播放动画**那一刻执行，所以 125Hz 主循环零开销；结果缓存 250 ms。

| 层 | 信号 | 覆盖面 |
| --- | --- | --- |
| 1 | `SHQueryUserNotificationState` | `RUNNING_D3D_FULL_SCREEN`=独占全屏游戏；`BUSY`=有全屏应用在跑（含全屏视频）；`PRESENTATION_MODE`=演示；`NOT_PRESENT`=锁屏 |
| 2 | 前台窗口是否铺满显示器 | 兜底那些不更新系统状态的程序 |
| 3 | 进程黑 / 白名单 | 用户自己的例外，白名单优先 |

第 1 层是关键：它**就是 Windows 判断"能不能打扰用户"的同一个 API**，系统本身就知道你在不在游戏里，比自己猜前台窗口靠谱。

两个必须讲清的细节：

- **最大化 ≠ 全屏。** 最大化窗口在 3072×1440 的屏上占约 95%，用「覆盖率 ≥96%」会把最大化的浏览器误判成全屏（这是实际发生过的 bug）。现在的判据是 **覆盖率 ≥99% 且窗口没有 `WS_MAXIMIZE`**。
- **多屏感知。** 全屏程序在 A 屏、光标在 B 屏时**照常放大** —— 你人并不在那个全屏应用里面。

### 4.5 托盘与菜单

`Shell_NotifyIconW` 挂一个图标，回调消息用 `WM_APP+1`。菜单是原生 `CreatePopupMenu` + `TrackPopupMenu`。

两处容易踩的坑（1.3.1 就是在修这两处，详见 §6.4、§6.5）：

- 托盘回调会收到**所有**鼠标事件（含 `WM_MOUSEMOVE`），不能按"不是双击就是点击"来写；
- 弹出菜单的**拥有者必须是前台窗口**，否则点外面关不掉。我们的叠加窗口是 `WS_EX_NOACTIVATE`，永远拿不到前台，所以另开了一个 1×1 全透明窗口专门当菜单所有者。

### 4.6 外观与帧缓存

| 参数 | 位置 | 范围 |
| --- | --- | --- |
| `appearance.scale` | settings.json | 1.5–6.0（越界收敛） |
| `appearance.color` | settings.json | `#RGB` / `#RRGGBB`（非法值回退黑） |

改动后重建帧缓存：**21 帧（3×）到 41 帧（5×）**，实测 40–160 ms。重建过程中没有动画在跑，所以用户感知不到卡顿。

手改 `settings.json` 也生效：主循环每 0.6 s 比对一次内存中的外观与配置。

### 4.7 配置与自动重启

`settings.json` **改动后自动重载**（比较 mtime），不用重启。

**配置与状态分开存放**（1.3.2 起）：

| 文件 | 内容 | 是否进仓库 |
| --- | --- | --- |
| `settings.json` | 用户配置（抑制项、名单、外观） | 是（同时充当模板） |
| `state.json` | 运行期状态，例如"引导气泡已展示过" | 否（`.gitignore`） |

分开的原因：状态标记写进 `settings.json` 会随模板一起被提交，导致**每个新克隆的人都看不到首次引导气泡**
（这个坑真的踩了两次）。状态是"这台机器记住的事"，不该跟配置混在一起。

自动重启（1.3.1）解决另一个问题：更新了 `shake_cursor.pyw` 之后，跑着的旧实例不会自己用上新代码。

```
每秒检查源文件 mtime
  → 变了就记下时间
  → 稳定 1.5 秒没有新改动
  → 启动新进程（带 --wait-pid <旧PID>）
  → 新进程等旧进程退出（避免抢单实例锁）→ 旧进程 quit
```

1.5 秒的等待是必要的：编辑器保存文件可能是多段写入，太早重启会读到半截文件。

## 5. 关键设计决策

| 决策 | 选择 | 被否掉的方案 / 原因 |
| --- | --- | --- |
| 识别方式 | 逐轴折返计数 | 速度阈值 —— 拖窗口/画圈误触 |
| 渲染方式 | GDI 4× 超采样 + 手写合成 | Direct2D（要多一层 COM 依赖）、PIL（破坏零依赖） |
| 帧资源 | 启动预渲染 21–41 帧 | 每帧实时绘制 —— 动画期间抖动 |
| 指针隐藏 | `SetSystemCursor` + 看门狗 | 不隐藏 —— 小箭头叠在大箭头里很难看 |
| 场景判定 | 先问系统（QUNS），再看几何 | 只扫进程名 —— 覆盖不全，且要维护清单 |
| 全屏判据 | 覆盖率 ≥99% 且非最大化 | 只看覆盖率 —— 最大化窗口会误判（真实 bug） |
| 菜单所有者 | 独立透明窗口 | 直接用在叠加窗口上 —— `NOACTIVATE` 拿不到前台，菜单关不掉 |
| 配置入口 | 托盘菜单 + JSON 双通道 | 只做 JSON —— 普通用户摸不到 |
| 更新机制 | 自重启 | 独立 updater —— 增加分发复杂度，且需要签名 |
| 依赖 | 零第三方 | 任何库 —— 会让"双击即用"变成"先装环境" |

## 6. 踩坑记录

这些是实际花掉时间的坑，按类别归档。

### 6.1 ctypes 必须声明 `argtypes`

不声明时，Python 的 `int` 会按 C `int`（32 位）传，**64 位句柄会被截断**：

- `CreateWindowExW` 少了 `argtypes` → 窗口静默创建失败（返回 NULL，没有任何异常）；
- `DefWindowProcW` 少了 `argtypes` → lParam 溢出，抛 `OverflowError`；
- `GetWindowLongW` 同理，会让 `WS_MAXIMIZE` 判断失真。

### 6.2 `WM_NCCREATE` 必须返回 `DefWindowProc` 的结果

测试里图省事让 `WndProc` 一律 `return 0`，结果窗口**根本创建不出来** —— `WM_NCCREATE` 返回 0 等于告诉系统"创建失败"。回调对象还必须存全局引用，否则被 GC 后崩溃。

### 6.3 前台锁：`SetForegroundWindow` 会静默失败

后台进程调用它会返回失败但**不报错**。需要先 `AttachThreadInput` 挂到当前前台线程，再抢前台。

**教训**：这类 API 必须检查结果（`GetForegroundWindow() == hwnd`），否则出错时你只会看到一个"关不掉"的菜单。

### 6.4 托盘回调不是"点击事件"

`uCallbackMessage` 会收到 `WM_MOUSEMOVE`、`WM_LBUTTONDOWN`、`WM_LBUTTONUP`、`WM_SETFOCUS`、键盘消息……

1.3.0 写成「不是双击就弹菜单」，于是**鼠标一划过图标菜单就出来**。正确写法是只认 `WM_RBUTTONUP`。

### 6.5 菜单是模态的，会重入

`TrackPopupMenu` 跑自己的消息循环，期间仍会派发消息。于是第二次回调在第一个菜单**里面**又开了一个菜单：关掉一层露出下一层，用户看到的就是"关不掉"。

必须加 `_menu_open` 之类的防重入标记。

### 6.6 Windows 11 会把新托盘图标折叠进 `^`

用户根本找不到入口。所以首次运行弹一次气泡提示，用 `tray_hint_shown` 标记控制只弹一次 —— 并且这个标记**不能**随模板提交进仓库（否则所有人都看不到提示）。

### 6.7 其他零碎

- `SHQueryUserNotificationState` 对**无边框全屏**也返回 `BUSY(2)`，不只对独占全屏。
- 全屏窗口用 `DWMWA_EXTENDED_FRAME_BOUNDS` 比 `GetWindowRect` 准；最大化窗口两者都会带上不可见边框，所以还得靠 `WS_MAXIMIZE` 兜底。
- 资源管理器重启会清掉托盘图标，要监听 `TaskbarCreated` 重新挂上。

## 7. 测试策略

**没有 CI 能验证的"手感"，但所有能自动化的都不靠肉眼。**

| 脚本 | 覆盖 |
| --- | --- |
| `tools/test_scene.py` | 真的创建无边框全屏窗口和最大化窗口，断言场景判定 |
| `tools/test_tray.py` | 菜单结构、点击过滤、防重入、黑名单切换、暂停状态、重启状态机 |
| `tools/test_appearance.py` | 三种颜色渲染后的主色像素、越界/坏值、帧缓存重建、菜单子项 |

三条原则：

1. **用真实窗口，不用 mock。** 窗口是系统行为，mock 掉就什么也没测到。
2. **不依赖前台状态。** `snapshot(pos, hwnd=...)` 支持注入句柄，绕开前台锁，测试可以在任何环境跑。
3. **不碰用户配置。** 测试通过 `SHAKE_CURSOR_SETTINGS` 环境变量指向临时文件（这条是踩过坑才加的：早期测试把用户真实的 `settings.json` 改掉了）。

CI（`.github/workflows/ci.yml`）做两件事：编译所有入口文件、断言 `settings.json` 结构。
注意 CI 用**单个 python 进程**编译所有文件 —— 多行 `run:` 块只取最后一条命令的退出码，中间失败会被吞掉（这个假绿持续了几天才发现）。

## 11. 资源占用

实测环境：Windows 11 / 16 核 / 3072×1440 @150% 缩放 / 外观 2.5 倍黑箭头 / 空闲态。

| 进程 | 任务管理器"内存"<br>（私有工作集） | 总工作集 | 私有提交 | 峰值工作集 | 线程 |
| --- | --- | --- | --- | --- | --- |
| 主进程 | ~15.5 MB | 34.3 MB | 17.0 MB | 35.2 MB | 4 |
| 看门狗 | ~12.3 MB | 21.9 MB | 14.1 MB | 21.9 MB | 2 |
| **合计** | **~28 MB** | 56 MB | 31 MB | — | 6 |

**主进程这 34 MB 工作集是怎么来的**（逐层加料实测）：

| 阶段 | 总工作集 | 私有提交 |
| --- | --- | --- |
| 裸 `pythonw` 空跑 | 19.9 MB | 10.9 MB |
| + 导入用到的标准库 | 20.2 MB | 12.2 MB |
| + 加载模块并预渲染 16 帧 | 23.2 MB | 14.5 MB |
| + 建窗口、消息循环、动画 | 34.3 MB | 17.0 MB |

结论：**约 11 MB 是 Python 解释器本身**，帧缓存只有 **0.2 MB**（2.5 倍时），
最后一层多出来的 11 MB 工作集里私有提交只占 2.5 MB —— 也就是说主要多为映射进来的系统 DLL / 绘制表面，
不是应用自己申请的内存。

其他：

- **CPU**：空闲时约占 **单核 1.9%**（整机 0.12%，16 核）。这是 125 Hz 轮询换来的响应速度，属于设计的固有成本。
- **句柄**：262 个；**GDI 对象 197 / 10000**、**USER 对象 17 / 10000**，距上限很远。
- **稳定性**：连续观察 8 分钟，工作集 34.3 MB 不变、峰值 35.2 MB，无明显增长（空闲态不泄漏）。
- **帧缓存随倍数变化**：2.5 倍 16 帧 / 0.2 MB，3 倍 21 帧 / 0.3 MB，5 倍 41 帧 / 1.4 MB。

如果哪天想砍内存，**唯一有意义的一刀是去掉看门狗**（省 ~12 MB），但它是"主进程崩了鼠标还能看见"的保险，
不建议动。其余优化（延迟构建帧、复用位图）收益都在 1 MB 以内，不值得增加复杂度。

## 12. 已知限制

| 限制 | 说明 |
| --- | --- |
| 只替换普通箭头 | 输入框的 I 型光标、链接的手型光标不受影响 —— 有意为之，不去掩盖指针当前的含义 |
| 独占全屏游戏里可能不显示 | 叠加窗口在独占全屏下会被挡；这类场景本来也已被场景感知抑制 |
| 白描边不可改 | 见 §4.2 的取舍 |
| 灵敏度不可调 | `SHAKE_*` 仍是代码常量 |
| `settings.json` 一物两用 | 既是仓库里的模板、又是用户的实盘配置，所以用户自己改过的值（比如倍数）会出现在 `git status` 里。运行期状态已拆到 `state.json`（见 §4.7），剩下的是配置本身；彻底解决需要拆出 `settings.example.json` |

## 13. 后续方向

按"用户可见收益 / 实现成本"排序：

1. **灵敏度可调** —— 现在 `SHAKE_*` 只能改代码，和"托盘可配"的设计不一致；
2. **配置文件与实际运行分离**（见 §12 最后一条）；
3. **按程序记住外观** —— 比如 PPT 里用大号白箭头，日常用小的；
4. **多显示器下的箭头位置微调** —— 贴近屏幕边缘时箭头会被裁掉一部分。
